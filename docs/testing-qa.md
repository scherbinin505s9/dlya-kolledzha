# Тестирование и QA (МДК.01.02, МДК.04.02, ОП.16)

Профиль колледжа АлтГУ — «Специалист по тестированию в области ИТ», поэтому этот раздел
стоит первым по важности после программирования.

## Виды тестирования

| Признак | Виды |
|---|---|
| По уровню | модульное (unit), интеграционное, системное, приёмочное |
| По цели | функциональное, нефункциональное (нагрузка, безопасность, удобство) |
| По доступу к коду | «чёрный ящик», «белый ящик», «серый ящик» |
| По моменту | дымовое (smoke), регрессионное, повторное |
| По исполнению | ручное, автоматизированное |

- **Smoke** — «а вообще запускается?» 5–10 ключевых проверок перед глубоким тестом.
- **Регрессия** — «не сломали ли старое, пока делали новое».
- **Unit** — проверяет одну функцию без БД и сети.

## Тест-кейс

Шаблон, который принимают на защите:

| Поле | Пример |
|---|---|
| ID | TC-01 |
| Название | Вход с корректным паролем |
| Предусловие | Пользователь зарегистрирован |
| Шаги | 1. Открыть форму входа. 2. Ввести `student@mail.ru` / `Pass1234`. 3. Нажать «Войти» |
| Ожидаемый результат | Открывается главная страница, в шапке имя пользователя |
| Фактический результат | — |
| Статус | Passed / Failed / Blocked |

Хороший тест-кейс: одна проверка, воспроизводимые шаги, конкретный ожидаемый результат.

## Чек-лист

Список проверок без детализации шагов. Пример для формы регистрации:

- [ ] пустые поля — кнопка неактивна
- [ ] email без `@` — сообщение об ошибке
- [ ] пароль короче 8 символов — ошибка
- [ ] пароли не совпадают — ошибка
- [ ] существующий email — «уже зарегистрирован»
- [ ] корректные данные — регистрация и переход
- [ ] повторное нажатие кнопки не создаёт дубль

## Баг-репорт

| Поле | Пример |
|---|---|
| Заголовок | Кнопка «Сохранить» не работает при пустом поле «Телефон» |
| Окружение | Windows 11, Chrome 141, версия 1.2.3 |
| Шаги | 1. Профиль → Редактировать. 2. Очистить «Телефон». 3. Нажать «Сохранить» |
| Ожидаемо | Показано сообщение «Заполните телефон» |
| Фактически | Кнопка не реагирует, ошибок в консоли нет |
| Серьёзность | Major |
| Приоритет | High |
| Вложения | скриншот, лог |

**Severity** — насколько сломан продукт. **Priority** — насколько срочно чинить.
Падение приложения = Critical/High, опечатка = Trivial/Low.

## Автотесты на Python (pytest)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install pytest
```

`test_calc.py`:

```python
from calc import add, divide
import pytest

def test_add_positive():
    assert add(2, 3) == 5

def test_add_negative():
    assert add(-2, -3) == -5

@pytest.mark.parametrize("a,b,expected", [
    (2, 2, 4),
    (0, 5, 5),
    (-1, 1, 0),
])
def test_add_table(a, b, expected):
    assert add(a, b) == expected

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)
```

```bash
pytest -v
pytest -k "add"
pytest --maxfail=1
```

Структура: `assert` + граничные случаи + проверка исключений. Не тестируйте всё подряд —
тестируйте логику и границы.

## Тестирование API

```bash
# успешный запрос и код ответа
curl -s -o /dev/null -w "%{http_code}\n" https://httpbin.org/status/200

# POST с JSON и проверкой поля
curl -s -X POST https://httpbin.org/post \
  -H "Content-Type: application/json" \
  -d '{"login":"student"}' | jq '.json.login'

# проверка заголовка авторизации
curl -s https://httpbin.org/headers -H "Authorization: Bearer test" | jq '.headers'
```

Postman: коллекция → запросы → Tests:

```javascript
pm.test("статус 200", () => pm.response.to.have.status(200));
pm.test("есть поле id", () => pm.expect(pm.response.json()).to.have.property("id"));
```

## Покрытие

```bash
pip install coverage
coverage run -m pytest
coverage report -m
```

100% покрытия не гарантирует отсутствие багов: покрытие показывает, какой код **выполнялся**,
а не правильно ли он работает.

## Демоэкзамен

Типовая структура задания по 09.02.07 (4 модуля, ~4 часа):

1. **Модуль 1.** Разработка модуля ПО (C#/Java/Python): консольное приложение или десктоп.
2. **Модуль 2.** Интеграция модулей: обмен данными, API, обработка ошибок.
3. **Модуль 3.** Разработка/тестирование: БД, SQL-запросы, тест-кейсы, баг-репорты.
4. **Модуль 4.** Сопровождение: развёртывание, инструкции, документация.

Что тренировать заранее:

- шаблон консольного проекта и быстрый старт без интернета;
- SQL: `SELECT`, `JOIN`, `GROUP BY`, `INSERT/UPDATE`, создание таблиц;
- оформление тест-кейсов и баг-репортов в таблице;
- Git: закоммитить и запушить результат;
- тайминг: 20 минут на настройку окружения — это норма, заложите их.

## Чек-лист сдачи лабораторной

- [ ] программа запускается на чистой машине по инструкции из README;
- [ ] есть тесты хотя бы на основную функцию;
- [ ] нет закоммиченных `bin/`, `obj/`, `.venv/`, `node_modules/`;
- [ ] имя репозитория и ветки осмысленные;
- [ ] скриншоты/логи работы приложены к отчёту;
- [ ] отчёт оформлен по требованиям — см. [reports-gost.md](reports-gost.md).

## Частые ошибки

| Ошибка | Как правильно |
|---|---|
| «Работает у меня» | фиксировать окружение: версия ОС, браузера, SDK |
| тест проверяет 5 вещей сразу | один тест — одна проверка |
| баг без шагов воспроизведения | шаги, ожидание, факт, окружение |
| `assert` без граничных случаев | пусто, ноль, максимум, отрицательные |
| тесты зависят от порядка запуска | каждый тест сам создаёт свои данные |
| тест лезет в настоящую БД | мок или отдельная тестовая база |
